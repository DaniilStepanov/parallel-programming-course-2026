## Ответы на вопросы

1. `collector-nostep3-1x1`
   ```
   > ./lab2 run collector-nostep3-1x1 dfs
   explored 106 schedules, 12 fail  (0.14 s)
   first failing: ABBBAABAAB -> LOST 1 record(s): counted 0 of 1
   
   > ./lab2 run collector-nostep3-1x1 replay ABBBAABAAB log
     A active -> 0
     B active -> 0
     B active = 1
     B await done
     A inside[W1] = 0
     A cnt[W1][0] -> 0
     B cnt[W1][0] -> 0
     A cnt[W1][0] = 1
     A inside[W1] = -1
     B cnt[W1][0] = 0
   schedule ABBBAABAAB -> LOST 1 record(s): counted 0 of 1
   ```
   Здесь поток A является писателем, а потом B — читателем. Они оба прочли один и тот же active (№1 и №2), но читатель успел переключить буфер (№3)
   и проверить, что в данный момент он не занят писателем (№4). Но читатель только после этого занимает буфер (№5), и т.к. проверки из-за nostep3 нет,
   он читает из счетчика (№6), что после делает и читатель (№7). После этого писатель пишет туда же инкрементированное значение (№8). Однако это
   обновление теряется, т.к. эта ячейка уже была прочтена читателем.

3. Минимальное K=2. 945 расписаний, что составляет 0.26% от количества расписаний при полном DFS.

5. Ответы:
   - Потому что с одними данными работают не только писатели, но и читатели. И пусть писатель один, но читатели все равно есть.
   - Потому что при plain попросту не происходит пауз, а потому возможностями планировщика не определить ошибку. 
   - Разница в том, что в случае с `acqrel` моделирование ошибочное, т.к. планировщик не моделирует `setRelease` и `getAcquire`. Для `ok` 
   используются обычные (volatile) `set` и `get`, которые моделируются корректно.

# 4. Результаты этапа 7 (Store Buffering)

Для тестов этого этапа использовался процессор `AMD Ryzen 7 5700X, 8/16`.

| Режим | (0, 0) есть? | Пояснение |
|---|---|---|
| `relaxed` / `plain` | + | Т.к. нет никакого порядка, видимость изменений не гарантируется между потоками |
| `acqrel` | + | Проявляется баг Деккера |
| `seqcst` / `volatile` | - | Все записи гарантированно сбрасываются к кэш до чтения |
| `naive` | - | Возможно, синхронизация между самими раундами не позволяет другим потокам поработать с теми же ячейками. А так как в naive ячейка всего одна, то и поток свой раунд отрабатывает так быстро, что другой поток не успевает приступить. |

## Размер пачки (задание 7.1)
| Команда | (0, 0), % |
|---|---|
| `acqrel 2000000 100` | 0, 0% |
| `acqrel 200000 100` | 70, ~0% |
| `acqrel 200 100000` | 23, ~0% |
| `acqrel 20 1000000` | 51, ~0% |
| `acqrel 20 10000000` | 34876, 0.017% |
| `acqrel 20 100000000` | 684, ~0% |

Насколько одновременно потоки проходят одни и те же ячейки зависит от размера cells, т.к. при небольшом размере после
старта (а стартуют они из-под барьера) потоку может повести пройти весь цикл разом. При большом размере cells вероятность
переключения задачи прямо во время перебора массива сильно повышается. Также может зависеть от частоты процессора, 
т.к. на производительном процессоре за квант времени поток сможет пройти больше ячеек.

Но это все в теории. На практике я не могу добиться увеличения `(0, 0)` никаким образом. Только для предпоследней строки есть аномалия, 
и то она проявляется редко.

3. Ответы:
   - Потому что в модели собственного планировщика все обновления `Shared<T>` всегда видны. В реальности такой гарантии нет.
   - Конкретно из моих тестов тяжело говорить, т.к. зависимость от стенда не проявилась у меня и, например, от `acqrel`. 
   Но предполагаю, что корректность `plain` зависит от того, как быстро отрабатывает один раунд.
